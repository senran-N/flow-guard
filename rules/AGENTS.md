# FlowGuard — 端到端水路（Source ➔ Branch ➔ Sink）开发准则

在修改或扩展任何代码仓库时，严禁仅凭局部文件视野“盲人摸象”式改代码。必须以**端到端因果水路（真实水源 `Source` ➔ 分流支路 `Branch` ➔ 真实终端 `Sink`）**为核心视角：

## 1. 动工前：用透视与蓝图代替盲目 `grep`
- **改逻辑先查水路（`flow_trace`）**：修改跨函数或跨文件逻辑前，优先调用 `flow-guard` MCP 的 `flow_trace` 工具（传入目标函数、类名或状态字段），一次性获取其**上游水源、途经分流阀、下游终端、状态唯一写入者（SSOT）及仓内可复用近似函数**，避免遗漏并列支流或重复造轮子。
- **接新功能先拿施工单（`flow_blueprint`）**：将隔离实验代码接入生产项目、或新增同类特性时，先调用 `flow_blueprint` 指定一个现有同类模块，按其生成的 **《进水口 ➔ 分流路由 ➔ 成对接口 ➔ 终端出水口》填空清单** 逐站接通，严禁只接入口不接出口。

## 2. 交卷前：确保“水路全通、废管拆净”（`flow_verify`）
- **禁止半截断流**：任何合入生产区的代码，上游必须连通真实 `Source`（UI/IPC/引擎周期/网络收包/读档），产出的状态下游必须流向真实 `Sink`（原生对象/发包/写档/UI 状态），且成对生命周期接口（如 `Save/Load`、`Send/Receive`、`Serialize/Deserialize`）必须双向闭合。
- **禁止留存废管与创可贴**：替换旧逻辑后，必须根据 `flow_verify` 给出的“0 水流废管清单”将废弃旧函数/旧文件彻底物理删除；严禁使用空 `catch {}`、静默返回假默认值或 `#[allow(dead_code)]` 掩盖断流问题。
